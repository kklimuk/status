# CLI

- **The first argument names the command.** `run(args, openApp)` sends `status summaries …` to `commands/summaries.ts` with the remaining arguments. It sends a bare `status`, or one whose first argument is an option, to `commands/status.ts` with all of them. Anything else is an unknown command. So `status --days 3 summaries` fails closed on a stray argument.
- **Each command parses its own options with `util.parseArgs` in strict mode.** An unknown command or option, a stray argument or a bad value fails closed: exit code 1, the reason on stderr, then the usage. Both commands read `--days <n>` (default 7) through `parseDays`, so they accept the same values.
- **`status --help` lists every command, and `status summaries --help` shows its own usage.** Each command exports its synopsis (`STATUS_USAGE`, `SUMMARIES_USAGE`), `usage(…)` formats synopses, and `src/cli/index.ts` lists them all.
- **`--days` runs from 1 to 3650.** A bigger value would put `since` past the range of a `Date`, and sync would compare against an invalid one.
- **Both commands bring the store up to date with `refresh(app, days)` before they read it:** `sync` over the window, then `refreshSummaries`. It never throws over an adapter or a summary. It returns:
  - `deferred`: busy roots whose family kept its summaries this run, so a command can mark them as behind;
  - `failed`: true when sync or a summary failed. The run is then half-finished, and the command prints what it has and exits 1;
  - `issues`: one line per failure (`failed: claude read <path>: …`, `failed: summary <id>: …`), then one per warning, ready to print after the command's own output. Empty when there are none.
- **A command opens the app only after its options parse,** by calling `openApp()`. So `--help` and a mistyped option never create `~/.status`. Tests pass an `openApp` that throws to check this.
- **An error a command throws fails closed** as `status: <message>` with exit code 1, without the usage.
- **Commands return `{ output, exitCode }` and never write.** `src/index.ts` writes the output: to stdout on success, to stderr on failure.
- **Color goes through `colorize(text, tone)`.** A tone is a semantic name mapped to a color in one `TONES` table: `heading` and `error`, plus `running`, `blocked`, `finished` and `muted` for session states and buckets. Commands never write escape codes themselves.
- **Piped output is always plain.** `Bun.color(…, "ansi")` emits escape codes even when the output isn't a terminal, so `src/index.ts` strips them with `Bun.stripANSI` unless the stream it writes to is a TTY. Agents read piped output, so this matters more than the color does.
- **`NO_COLOR` already works.** `Bun.color` returns an empty string when it's set, and `colorize` then returns the text unchanged.

## `status`

The human's morning triage: root sessions active in the `--days` window, grouped by goal, each in a bucket (blocked on you, running, finished) with one line. Subagents are folded into their root.
- **Opus picks each session's bucket, and code never overrides it,** not even for `waiting` or `busy`. The user decided this on 2026-10-23 after reading the first version's rule table, which derived the bucket in code from the live state and the summary: they want Opus's judgment, which can weigh an old, unanswered ask on an ended session or a summary that lags the session. The prompt defines the buckets by meaning, by who has the next move:
  - blocked: the developer's;
  - running: an agent or something external is making progress;
  - finished: nothing is left for anyone.

  It also says what each live state means: `waiting` is a prompt or question open now, `busy` is a turn in progress, `idle` is a turn that ended with the session still open, `ended` is a process that's gone. A subagent's state counts toward its root, and an `idle` one (Codex) waits on its root, not the developer.
- **The window is family activity:** a root is in it when it or any subagent has `last_event_at` within `--days`.
- **A summary is behind** when the root has none, or when the newest event id across its family is past its `through_event_id`, the same rule `status summaries` uses. That covers deferred and failed summaries alike. Opus is told, and the session shows `summary behind`.
- **Opus input:** per root, its live state, title, directory, branch, last activity (time and age), each subagent that isn't `ended` with its state and objective, and the summary without `tried`, which doesn't bear on buckets, goals or one line.
- **Opus's answer is checked against the input.** The schema lists the input's ids and the three buckets as enums, so the CLI's schema check sends a bad value back to Opus within the call; the code check is the backstop. An id it wasn't given, an id listed twice, or a bucket outside the three rejects the whole answer: every session is shown under `Not grouped` with its objective, followed by `failed: grouping by goal: …`, and the run exits 1. A session it left out is shown under `Not grouped` with a warning, and the run still exits 0, since every session is on screen. A failed call fails the same way as a rejected answer.
- **A `Not grouped` session has no bucket.** It's printed without a bucket heading, after the goals, and counted apart in the tally (`· 1 not grouped`). When the whole answer was rejected, the tally shows only that count, since no session was judged and `0 blocked on you` would claim otherwise.
- **The ask is printed verbatim** under a session Opus put in blocked, or one under `Not grouped`, from its summary. A `waiting` session, or one with a `waiting` subagent, without one says where a prompt or question is open. A failed grouping puts every session under `Not grouped`, and the open questions are what the developer still needs from that degraded run.
- **Goals are ordered by their most urgent bucket, then by latest activity;** buckets within a goal go blocked, running, finished, and sessions within a bucket by latest activity. Opus's order isn't used.
- **No session in the window prints one line and makes no Opus call.**

## `status summaries`

Agents read it before they act, so its output is compact plain text in a stable shape.
- **The default list is live sessions (`busy`, `idle`, `waiting`); `--all` adds ended ones whose last event is inside `--days`.** A listed session nests under its nearest listed ancestor. When that isn't its parent, because the parent is ended or hidden, the entry gets a `parent:` line, so a subagent of a hidden root moves to the top level with one. Sessions go newest-started first, then by id, so the order holds while they work.
- **Each entry is a headline (id, state, `active <age>`, and `summary behind` or `no summary yet`), then one `label: value` line per field.** A value that spans lines (an `ask` with its options, say) continues on lines indented under its label, so every line stays inside its entry. The id carries the harness (`claude:…`, `codex:…`). The summary's list columns print one `- item` per line, an empty one prints `none`, and `ask` shows only with `waiting on user`.
- **A summary is behind when the newest event across its session and its subagents is past its `through_event_id`.** That's summaries' own staleness rule, computed in the command from `newestEventIdBySession` and `summariesBySession` after `refresh` (as `status.ts` does), so it covers a deferred busy family and a summary that failed this run without parsing `issues`. A deferred family member whose summary already covers its family isn't marked.
- **Files edited in the last 30 minutes** are the targets of `Edit`, `MultiEdit`, `Write`, `NotebookEdit` (Claude) and `apply_patch` (Codex, one file per line) with status `ok` or `pending`. A refused or failed edit changed nothing. A session without an entry of its own (an ended subagent in the default list) adds its edits to the nearest entry above it, because a root that delegates its edits would otherwise show none. The caller's own family adds nothing, so its edits never read as another session's.
- **`--session <id>` shows one session whatever its state:** its entry, with its subagents' edits in it, every subagent below it (a headline, title and objective each), and its last 20 tool calls oldest first, each target cut at 300 characters like a summary's input. Every printed id works with it. An unknown id fails closed, after `refresh`, so a session that just started is found.
- **Only the caller's own session is left out, never its subagents;** they're listed at the top level with `parent: <id> (this session)`.
  - Claude: walk up from `status`'s own pid, one `ps -o ppid=,lstart=` per hop, until `<claude>/sessions/<pid>.json` names that pid with a matching `procStart`. That's the Claude process, so under a subagent the walk finds the root session, not the subagent: a stream agent sees its sibling streams, and itself as one of its root's subagents. A pid that `ps` doesn't list ends the walk; `ps` itself failing adds a `warning:` line, since the caller may then be listed.
  - Codex: `CODEX_THREAD_ID`, which Codex sets in a tool's shell (the name sits among the exec environment variables in the 0.163 binary), names the exact thread, subagent or root.

# Summaries

`refreshSummaries(app, scope)` keeps one rolling Haiku summary per session in `summaries`, subagents included, so an agent or the user can act on a session without opening its transcript. A subagent's summary feeds its parent's. It reads `sessions` and `events`, which sync writes, and owns every read and write of `summaries`, with one exception: when an interactive Claude session moves into a background job, sync deletes the old session, its events and its summary, and reparents its subagents to the continuation, so a summary can vanish without summaries doing it.
- **`refresh.ts` keeps the summaries up to date** (`refreshSummaries`: planning, the calls, chunks, storage and progress). **`prompt.ts` is what Haiku sees and returns:** the system prompt, the schema, the input rendering and `parseSummary`. **`catalog.ts` is what the `status summaries` commands read** (see The catalog). **`utils.ts` holds the shared selectors,** `summariesBySession` and `newestEventIdBySession`, which `@src/statuses` reads too. `index.ts` re-exports all four.
- **The catalog is plain data and never renders.** The CLI lays out and colors the table and the `get` view (`src/cli/AGENTS.md`).

## The report

`refreshSummaries` returns a `SummaryReport` and never throws for one session's failure:
- `roots` and `subagents`: each a `SummaryTally` of sessions `refreshed` (their summary now covers their newest event), Haiku `calls` made and the `inputTokens` they billed, retries included. They're apart so a subagent's cost shows: every subagent gets its own calls.
- `deferred`: busy roots whose summary is under 15 minutes old, kept as is with their subagents' (see Staleness). They're ids, so a command can mark those families' summaries as behind.
- `warnings`: calls whose largest prompt crossed the 100,000-token price tier, with the estimate the chunk was cut by, so the estimate can be tuned.
- `failures`: each `SummaryIssue` names the session and the error. **A non-empty `failures` means the run is half-finished,** and the commands exit non-zero on it, as with sync's. The failed session keeps its old summary, whose `through_event_id` and `updated_at` still say how far it reaches, so it never passes for fresh.

## Staleness

- **A session is stale when the newest event id across it and its subagents is past its `through_event_id`.** Event ids are global ingest order, so one number covers a session's whole family. A subagent's events are its own session's rows, so a parent with no new events of its own still goes stale when a subagent works.
- **Subagents are found at any depth through `parent_id`** (a Claude or Codex subagent can spawn its own, and points at the agent that did). A root is a session without a `parent_id`. A subagent whose parent isn't stored is never summarized, because no family reaches it.
- **A busy root keeps its family's summaries while its own is younger than 15 minutes.** `status summaries list` runs often, and a busy session changes on every run. Only the root's own state counts, and its subagents wait with it: a subagent runs inside its parent's work, so throttling them apart would only refresh a parent against a stale child. Any other state isn't throttled: an `idle` or `waiting` root (blocked on a permission prompt or question) may be waiting on the user, which is exactly when a fresh summary matters. A root without a summary is summarized whatever its state.
- **A tool result that only changes a status isn't seen.** It updates its call's row in place and keeps the id, so `pending` → `user_denied` or `ok` moves no id past `through_event_id`. That's accepted:
  - A status change is almost never the last thing a session writes. A Claude rejection is followed by a `[Request interrupted by user for tool use]` user message, which the adapter keeps for this reason; an approval runs the tool and the assistant answers; a Codex model replies to a declined command. Each is a new id.
  - Seeing it wouldn't be enough. The rolling input holds only events past `through_event_id`, so the changed row wouldn't be in it, and the call would restate the old summary.
  - What's left is a session that dies right after a tool result: its summary can call that tool pending, next to a live state of `ended`.
  - If the real-data pass shows misses: sync's `last_event_at` includes tool-result times, so `last_event_at > updated_at` across the family flags the change, and the next call would then have to re-send the covered calls of the last turn.

## Coverage

- **Planning reads in one transaction,** through the transaction's handle. Each due session's `through_event_id` is its family's newest id in that snapshot, and its own events are read up to that id, so an event ingested by another run meanwhile is covered next time, not claimed now.
- **Subagents are summarized before their parents, deepest level first,** so a parent reads its subagents' fresh summaries. With every subagent at or past the planned id, the parent's `through_event_id` is honest for the whole family.
- **A parent whose changed subagent's summary is behind isn't refreshed.** That's a subagent that failed in this run, or one with no summary: the parent fails too, naming the subagent it waits for, and keeps its old summary. One failure deep in a family therefore fails each ancestor up to the root.
- **A refresh is stored only after its last chunk succeeds.** Entries are cut into chunks in time order, but ids are ingest order (a subagent's file can be ingested after its parent's), so a chunk boundary isn't an id boundary that a partial summary could claim. A failure in any chunk keeps the old summary.
- **A stored summary is never replaced by one that covers fewer events.** The upsert only overwrites when the new `through_event_id` is at least the stored one, because two runs at once (agents run `status summaries list` in parallel) can finish out of order.
- **Every stale session gets a call.** It has new events of its own, or a subagent whose family moved, which adds that subagent's summary as an entry. A busy subagent therefore costs a call for itself and one for each ancestor on every run that isn't deferred.
- **At most 10 sessions are summarized at once,** each one's chunks in sequence. Each depth finishes before the next one up starts. Within a depth, sessions go in order of their root's latest event, newest first.

## Scoped refresh

- **`refreshSummaries(app, { sessionId })` brings one session and its descendants up to date,** for `status summaries get`. They're what its summary is built from; its parent isn't, so the parent and every other family are left alone.
- **The busy-root deferral doesn't apply to a scoped refresh:** the caller asked for this session by name, so a busy one is refreshed even with a summary under 15 minutes old. `deferred` is then always empty.
- **The scope is planned like a root,** with depths counted from it, so its deepest descendants still go first. A subagent whose parent isn't stored, which no unscoped run reaches, is summarized when it's the scope.
- **An unknown id plans nothing** and makes no call. The command fails closed on it after the refresh.

## The catalog

`readCatalog(app)` reads, after the refresh, everything `status summaries list` and `get` show: every stored session (newest-started first, then by id), its children, the stored summaries, the set of summaries that are behind, and the edit calls of the last 30 minutes.
- **A summary is behind when the newest event across its session and its subagents is past its `through_event_id`.** That's the staleness rule above, read after the refresh, so it covers a deferred busy family and a summary that failed this run without parsing the report's failures. A deferred family member whose summary already covers its family isn't marked. A session without a summary isn't in the set; the commands show it as having none.
- **`listSessions(catalog, { callers, all, since })` returns the listed sessions in display order, each with its depth and edited files.** Listed means not a caller, and live (`busy`, `idle`, `waiting`), or, with `all`, ended with a last event at or after `since`. A listed session sits under its nearest listed ancestor, depth-first in catalog order; one with none is at depth 0, subagent or not.
- **Edited files are the targets of `Edit`, `MultiEdit`, `Write`, `NotebookEdit` (Claude) and `apply_patch` (Codex, one file per line) with status `ok` or `pending`, newest first.** A refused or failed edit changed nothing. A session that isn't listed (an ended subagent in the default list) adds its edits to the nearest listed session above it, because a root that delegates its edits would otherwise show none. A caller's own family adds nothing, so its edits never read as another session's. `filesEditedBy(catalog, id)` gives one session's, its subagents' included, for `get`.
- **`sessionsMatching(database, idOrPrefix)` resolves `get`'s argument:** an exact id matches only itself; otherwise every id the prefix starts, in id order. `onlyMatch` picks the one match, if there's exactly one.
- **`recentToolCalls(database, id, RECENT_TOOL_CALLS)`** gives a session's last 20 tool calls, newest first.
- **`callerSessionIds(app)` is the session running `status`,** so `list` can leave it out: `codex:$CODEX_THREAD_ID` (`codexSessionIn`) and the Claude session above `status`'s own pid (`claudeSessionAbove`), each the harness's own rule (`src/harnesses/AGENTS.md`, "Self-identification"). When the Claude walk fails, it returns a warning instead of failing the command, because the caller may then be listed.

## Progress

Through `app.progress("summaries", …)`, which only a terminal sees (`src/cli/AGENTS.md`):
- the busy roots deferred, with their ids, then how many sessions are due (and how many of them are subagents), or, with nothing due, `nothing else to refresh` after a deferral and `every summary is current` without one;
- each session as it starts (`started 3/12 <id> · <title>`) and as it finishes, with how long it took and its calls, or fails, with the error. The title is cut at 60 characters. Durations come from `app.now()`, so tests can pin them;
- when anything was due, the totals: refreshed, failed, over the price tier, calls and input tokens.

## Input

- **A header names the session's title and working directory,** and `Subagent of: <parent id>` for a subagent. The prompt doesn't ask for paths relative to the directory, because sync keeps the latest `cwd`, which moves when a session changes worktree, and items written earlier would silently change base.
- **Entries in time order, each with its UTC minute:**
  - user and assistant messages in full, never cut: the project decided a message is never cut, so a summary sees what was actually said;
  - tool calls as one line: the tool name and target (several targets joined with commas), or the headline when there's no target, cut at 300 characters, with the status as stored (`ok`, `error`, `user_denied`, `auto_denied`, `pending`). Tool output isn't stored;
  - **each direct subagent whose family moved since the session's last summary, as its current summary,** rendered like the summary so far and placed at the latest `last_event_at` across the subagent and its own subagents, where its family was last active, since that's how far its summary reaches. A subagent that didn't move stays out: the summary so far already has it. A subagent's own events never go into its parent's input.
- **A subagent's own input is its whole transcript, like any session's.** Its first user message is its task, written by the parent. A Claude workflow agent's first two are `[Workflow harness — user request]` (the user's request, shared by every agent) and `[Workflow harness — computed task]`, its own. A Codex subagent's task is encrypted: the adapter keeps the plaintext header (`Message Type`, `Task name: /root/<name>`, `Sender`) and ends it with `Payload:` and `[encrypted payload]`, so the objective comes from the task name and what the subagent did. The parent's history before the spawn is in the parent's own summary.
- **A later chunk or refresh gets the summary so far and only the entries past it.** The first user message is an ordinary entry in a fresh summary's first chunk and isn't repeated after it. The objective is carried by the summary itself and pinned by the prompt: the objective in the summary so far stays as written, and changes only when the entries show the goal itself critically changed (the user redirected, replaced or narrowed it), never reworded to describe the latest activity. Re-sending the first message cost a whole message per call and anchored on the wrong text in two cases: a session the user redirected, whose first message no longer states the goal, and a Claude workflow agent, whose first message is the request shared by every agent rather than its own computed task.
- **Live state stays out.** A summary changes only when events arrive, so it has to stay true while the state goes from busy to idle to ended. The readers show the live state next to it.

## Chunks and tokens

- **The 100,000-token price tier applies per request,** to the whole prompt: the CLI's own preamble, the system prompt, the schema, the summary so far and the entries. Crossing it makes the whole prompt cost 5x.
- **Entries are cut at about 85,000 estimated tokens per chunk, at 2 UTF-8 bytes per token.** That leaves about 15,000 for the rest: the CLI's preamble, the system prompt, the schema and the summary so far.
- **A message bigger than the chunk budget goes whole into a chunk of its own,** never split or cut. Its prompt can cross the price tier, and the `largestPromptTokens` warning then reports that chunk, so a costly one stays visible. The chunker closes the current chunk before such a message and after it, so it can't loop on it or drop it.
- **Bytes, not characters,** because a character outside ASCII takes 2 to 4 bytes and is often a token or more on its own. Counted in characters, a CJK chunk of 170,000 characters would send well over 100,000 tokens. For ASCII the two counts are the same.
- **Why 2 and not 4:** measured on 2026-10-23, a real Claude transcript ran 2.2 to 2.3 characters per token (paths, hashes and shell commands), and the synthetic prose fixtures about 3.2. At 4, a real 341,000-character chunk estimated at 85,000 tokens sent a 150,451-token prompt. At 2, the same transcript's chunks were 75,000 to 80,000 tokens.
- **Warnings compare `largestPromptTokens`, not `inputTokens`** (root `AGENTS.md`, "Calling Claude"). A call the CLI retried bills about twice its prompt.

## Storage

- **`progress`, `tried`, `next` and `blockers` hold one item per line,** and an empty column means no items. Haiku returns them as arrays; whitespace inside an item is collapsed, so an item never spans lines.
- **An `ask` comes exactly with `waiting_on: user`, and a `done` session waits on no one.** The schema states both rules with `if`/`then`, so the CLI's schema check sends a contradiction back to Haiku within the call; on 2026-10-23 a provoked `done` with `waiting_on: user` came back as `in_progress`. A blank `ask` is null.
- **Haiku's answer is checked against the schema in code** before it's stored, both rules included. A missing field, an unknown `waiting_on` or `outcome`, or a contradiction fails that session, like a failed call. An `ask` with another `waiting_on` used to be dropped silently, which under the done rule below would hide an offer.

## The prompt

The prompt is the feature: a summary is only useful if an agent can act on it without the transcript. What it settles, and why:
- **Two readers, named in the prompt.** Agents need exact paths, commands, hashes and errors, and what already failed. The user's triage needs what finished, what's running and what's waiting on them.
- **`objective`, `progress` and `blockers` are written for `status list`'s goal brief,** which tells the user, per goal, what it is overall, what was done, what stands in the way and what to do next. Opus builds it from the summaries alone, so they have to carry those things:
  - `objective` has two parts, written as "Goal: … This session: …": the larger goal (the project, why it matters, what done looks like) and this session's part in it. A narrow objective ("fix the parser test") left Opus nothing to say what a goal is overall or when it's done. A subagent's Goal is what its launching agent is working toward, and its part is its task. The pin rule still holds: a rolling update keeps the objective as written unless the goal itself critically changed, so a summary written before this rule keeps its narrow objective until the session is re-summarized from scratch.
  - `progress` is milestones with evidence (commits with hash, test counts, files), most important first, with the steps of one milestone merged and trivia left out. The brief's "Done" list is milestones, and a step-by-step log buried them.
  - `blockers` are written for the user: what stands in the way and why it matters, readable without the transcript. The brief shows them as its "Blockers" without the transcript behind them.
- **Field boundaries are spelled out, because Haiku blurs them otherwise:**
  - `tried` holds failed or dropped approaches with why: errors, rejected attempts, denied calls, a subagent's search that came up empty. It doesn't hold open problems (`blockers`), problems since solved (`progress`, with the fix) or trivia like a typo fixed on the next try.
  - `blockers`, `waiting_on` and `ask` describe the same stop from three sides, and the prompt names each one's question: what is stuck, who has the next move, and what exactly the user must decide. A blocker names the obstacle and doesn't restate the ask. An unanswered question is the `ask`, not a blocker.
  - `blockers` holds only what stops progress now. A dead end the session routed around is a `tried` item.
  - `next` holds only steps the session stated or committed to. Haiku used to add a review or a wider test run of its own, and a rolling update then carried it forward ("as the prior plan stated"), which kept a finished session `in_progress`. An offer still waiting on the user's answer is the `ask`, not a `next` step.
- **If there's still work to be done, it's not done.** `done` means nothing is left: the latest report says the work is finished and proposes nothing further. A session that ends offering or proposing more work ("Want me to push and open a PR?") is `in_progress` and `waiting_on: user`, and the `ask` is the offer as a yes-or-no question. The user decided this on 2026-10-23, reversing the first version, which called such a session `done` and put the offer in `next` as "Offered: …". Checked on real sessions, the old rule also wobbled: one session flipped between `done` and `in_progress` across runs, and another came back `done` while `waiting_on: user`.
- **The `ask` is self-contained:** what is being decided, the options with the session's recommendation, and the context needed to answer.
- **Rolling updates carry `progress` and `tried` forward.** Without that rule, a four-chunk session's final `tried` kept only the last chunk's trivia (a `/tmp/null` typo, an ECONNRESET) and lost the dead ends from the first three.
- **A denied call means two different things, and the prompt keeps them apart.** The status is rendered as stored:
  - `user_denied`: a person rejected the call, so the user has already said no. It goes in `tried` with the user's reason when the transcript gives one, and the `ask` never asks to approve it again.
  - `auto_denied`: an automatic reviewer refused it (Claude's auto-mode classifier, Codex's guardian) and no human decided. It's a blocker when the session stalled on it, since the agent may need the user's manual approval or another approach, and a `tried` item when the session worked around it.
- **One prompt serves roots and subagents,** with a "Subagent sessions" section that applies when the header says `Subagent of`. A subagent reports to the agent that launched it, not to the user, so an offer or suggestion in its report isn't an `ask`, it's `done` when its report says the task is finished, and `waiting_on: user` means a person must act (a permission it stopped on). Its objective is its own task: the computed task for a workflow agent, and for a Codex subagent the task name and its actions, stated without notes on how it was inferred (Haiku added "(task name /root/critic, inferred from …)" otherwise).
- **A `SubagentHandback` call is a Claude subagent's report.** The adapter stores only the tool's name, not the report, so without that line Haiku called a subagent that had handed back `in_progress`, with "report to the parent" as `next`.
- **In a parent, a subagent's findings and dead ends are its own, but a subagent's suggestion is a `next` step only once the parent takes it up.** Haiku otherwise turned a critic subagent's ideas for a later study into the parent's `next`. A subagent waiting on the user means its parent is too.
- **Enum values are written bare in the prompt.** That alone didn't stop Haiku returning `"\"user\""`: the cause was how the CLI's tool call encodes top-level fields, and `askClaude` now nests the schema (root `AGENTS.md`, "Calling Claude").

The prompt was checked against real Haiku on hard-case fixtures: a session ending on a question (then answered), a recap after a commit, subagents hitting dead ends, a denied and abandoned publish, and a real four-chunk transcript. The done rule was re-checked on a recap after a commit that offers to push and open a PR, a finished session that offers nothing, and four real sessions. Subagent summaries were checked on three real families (three Codex subagents with encrypted tasks, a Claude review subagent, and a Claude subagent that handed back), and on a rolling update where one subagent changed after its parent was summarized. The fixtures and probes were scratch files in each stream's worktree, so they aren't kept. To repeat the check, rebuild those cases as rows in a temporary `STATUS_HOME` and run `refreshSummaries` on it.
